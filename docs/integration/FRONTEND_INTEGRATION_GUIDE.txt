SECTION 1: CRITICAL STATUS ENUM CORRECTIONS
================================================================================

IMPORTANT: ALL status values in the backend are 1-BASED (start from 1, not 0).
The frontend currently uses 0-based. This MUST be fixed everywhere.

--- INDENT STATUS (from IndentStatus.java → tbl_indent_status table) ---

  1 = Draft              (initial creation)
  2 = Submitted          (pending HOD approval)
  3 = Department Head Approved (L1 approved)
  4 = Finance Approved   (L2 approved)
  5 = Procurement Approved / PO Created
  6 = Rejected           (rejected at any level)
  7 = On Hold            (legacy hold status)
  8 = Completed          (fully done)

  Note: IndentStatus is a JPA entity mapped to tbl_indent_status table.
  The status field on Indent is a FK to this table (not a plain integer).
  The Response DTO returns both the status ID and status name.


--- PO STATUS (from PurchaseOrder.java → po_status column, plain integer) ---

  1 = Draft
  2 = Submitted           (pending approval)
  3 = Approved
  4 = Sent to Vendor
  5 = Partially Received
  6 = Fully Received
  7 = Cancelled
  8 = Closed

  Frontend WRONG mapping: DRAFT=0, PENDING=1, CONFIRMED=2
  Frontend CORRECT mapping: DRAFT=1, SUBMITTED=2, APPROVED=3, SENT_TO_VENDOR=4,
                            PARTIALLY_RECEIVED=5, FULLY_RECEIVED=6, CANCELLED=7, CLOSED=8

  Business rules:
  - Can edit:          only when status = 1 (Draft)
  - Can approve:       only when status = 2 (Submitted)
  - Can send to vendor: only when status = 3 (Approved)
  - Can receive goods: only when status = 4 or 5 (Sent/Partially Received)
  - Can cancel:        any status except 7 (Cancelled), 8 (Closed), 6 (Fully Received)


--- GRN STATUS (from GoodsReceipt.java → goods_receipt_status column) ---

  1 = Created             (pending inspection)
  2 = Inspected           (pending RM approval)
  3 = RM Approved         (pending Dept Head approval)
  4 = Approved            (pending final approval)
  5 = Final Approved      (pending storage)
  6 = Stored              (completed — goods in inventory)
  7 = Rejected

  Frontend WRONG mapping: DRAFT=0, PENDING_QC=1, QC_APPROVED=2
  Frontend CORRECT mapping: CREATED=1, INSPECTED=2, RM_APPROVED=3, APPROVED=4,
                            FINAL_APPROVED=5, STORED=6, REJECTED=7

  GRN has a "supervisorBypass" boolean flag:
  - If true, skip RM approval step (status jumps from 2→4)
  - If false, normal flow: 1→2→3→4→5→6

  Business rules:
  - Can inspect:       only when status = 1
  - Can RM approve:    only when status = 2 AND supervisorBypass = false
  - Can approve:       when status = 3 OR (status = 2 AND supervisorBypass = true)
  - Can final approve: only when status = 4
  - Can store:         only when status = 5
  - Can reject:        any status except 6 (Stored) and 7 (Rejected)


--- ISSUE NOTE STATUS (from IssueNote.java → issue_note_status column) ---

  1  = Created             (draft)
  2  = Pending RM Approval (submitted)
  3  = RM Approved         (pending manager approval)
  4  = Approved by Manager (ready for stores)
  5  = Rejected by RM
  6  = Rejected by Manager
  7  = Pending Store Issue  (waiting for stores to issue)
  8  = Issued              (materials released — done)
  9  = Rejected by Stores  (insufficient stock)
  10 = Returned            (materials returned to stores)

  Frontend WRONG mapping: DRAFT=0, PENDING_APPROVAL=1, APPROVED=2
  Frontend CORRECT mapping: use exact values 1-10 above

  Issue Note also has "supervisorBypass" flag:
  - If true, skip RM approval (status jumps from 2→4 on manager approval)
  - If false, normal flow: 1→2→3→4→7→8

  Business rules:
  - Can submit:           only when status = 1
  - Can RM approve:       only when status = 2 AND supervisorBypass = false
  - Can manager approve:  when status = 3 OR (status = 2 AND supervisorBypass = true)
  - Can issue goods:      when status = 4 or 7
  - Can stores reject:    when status = 4 or 7
  - Can cancel:           when status = 1 or 2
  - Can return:           only when status = 8 (Issued)
  - Rejected states: 5, 6, 9 (three different rejection reasons)

SECTION 5: INVENTORY API — RESPONSE FORMAT & ENDPOINTS
================================================================================

The Inventory module does NOT use Spring Page<T>.
It uses a custom Map<String, Object> response wrapper:

  {
    "success": true,
    "count": 5,
    "data": [ ... inventory items ... ]
  }

Error responses:
  {
    "success": false,
    "error": "Insufficient Stock",
    "message": "..."
  }

All Inventory Endpoints (base: /api/v1/inventory):

  GET    /api/v1/inventory                                         → List with filters (companyId, plantId, materialId, lowStock)
  GET    /api/v1/inventory/stock/{materialId}/plant/{plantId}      → Get stock for material at plant
  GET    /api/v1/inventory/stock/plant/{plantId}/company/{companyId} → Bulk: all materials at plant
  GET    /api/v1/inventory/low-stock                               → Low stock items
  GET    /api/v1/inventory/critical-stock                          → Critical stock items
  GET    /api/v1/inventory/statistics                              → Statistics (companyId)
  POST   /api/v1/inventory/adjustment                              → Stock adjustment
  GET    /api/v1/inventory/transactions                            → Transaction history (many filters)
  GET    /api/v1/inventory/check-stock/{materialId}/plant/{plantId}?requiredQuantity=100  → Check single
  POST   /api/v1/inventory/check-stock-bulk?plantId=1              → Bulk availability check

  Note: Transaction history accepts filters: companyId, plantId, materialId,
        transactionType, direction, startDate, endDate (ISO 8601 format)

SECTION 9: KEY BUSINESS LOGIC THE FRONTEND SHOULD KNOW
================================================================================

1. INDENT → PO FLOW:
   - Only indents with status=5 (Procurement Approved) can become POs
   - One indent creates one PO
   - Creating a PO updates the indent status to 4 (Finance Approved / PO Created)
   - PO number format: PO/YYYY/NNNNN (auto-generated)

2. PO → GRN FLOW:
   - GRN is created AGAINST a PO's indent
   - GRN validates: received qty cannot exceed PO ordered qty
   - Multiple partial GRNs allowed per PO
   - Final GRN approval (status=5) adds goods to inventory automatically

3. ISSUE NOTE → INVENTORY FLOW:
   - Issue note DEDUCTS from inventory when status=8 (Issued)
   - Return (status=10) ADDS back to inventory
   - Stores rejection (status=9) = insufficient stock, no inventory change

4. DOCUMENT NUMBERING:
   - Indian Financial Year format: IND/2024-25/0001
   - FY starts April, ends March
   - Auto-reset counter at FY boundary
   - Company-based prefixes

5. AUDIT LOGGING:
   - Backend logs ALL CRUD operations to tbl_audit_log
   - Frontend doesn't need to send audit data — backend handles it automatically
   - Audit captures: entity type, old/new values (JSON), user, IP, timestamp

6. SUPERVISOR BYPASS:
   - Both GRN and Issue Note support "supervisorBypass" flag
   - When true: skips RM (Reporting Manager) approval step
   - This affects the status flow the frontend needs to display

SECTION 11: EXTRA INSIGHTS FOR FRONTEND TEAM
================================================================================

1. CORS: Backend has CORS configured. If frontend gets CORS errors, check that
   the frontend origin is added to WebConfig.java's allowed origins list.

2. DATE FORMATS: Backend uses ISO 8601 formats:
   - LocalDate: "2025-03-15"
   - LocalDateTime: "2025-03-15T10:30:00"
   Frontend should send/receive dates in these formats.

3. PAGINATION: All paginated endpoints use 0-indexed pages.
   First page = 0, not 1.

4. ERROR HANDLING: Backend uses Spring's standard error response:
   {
     "timestamp": "2025-...",
     "status": 400,
     "error": "Bad Request",
     "message": "Validation failed",
     "path": "/api/v1/indents"
   }
   Exception: Inventory module uses { success: false, error, message }

5. DECIMAL PRECISION: All monetary and quantity fields use decimal(20,2).
   Frontend should display 2 decimal places for amounts and quantities.

6. STATUS FIELD NAMING IN RESPONSES:
   - PO: returns both "poStatus" (integer) and "poStatusName" (string)
   - GRN: returns "status" (integer) + getStatusName() method generates string
   - Issue Note: returns "status" (integer) + getStatusDescription() method
   - Indent: returns nested "status" object (IndentStatus entity with id + name)

7. FILE UPLOADS: Material bulk import expects multipart/form-data with CSV file.

8. ACTUATOR: Health check available at GET /actuator/health (no auth required).
   Frontend can use this for backend connectivity check.
